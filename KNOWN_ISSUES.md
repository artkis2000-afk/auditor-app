# KNOWN ISSUES

Реестр расхождений/сомнительной логики, обнаруженных при reverse engineering исходного
приложения. Правило: логика переносится **как есть** (функциональная эквивалентность),
фиксируется тестом, а улучшение обсуждается и выполняется ОТДЕЛЬНЫМ этапом.

Статусы: `OPEN` (перенесено как есть, ждёт обсуждения) · `DISCUSSING` · `RESOLVED`.

## KI-1 — `suspicious_supplier`: тип аномалии объявлен, но не реализован
- **Статус:** OPEN
- **Где (исходник):** `фуры/src/types.ts` (`AnomalyFlagType`), `фуры/anomalyDetector.ts`
- **Суть:** Тип флага `suspicious_supplier` присутствует в типах, но ни одно правило в исходном
  детекторе его не создаёт. Поле `Supplier.isApproved` существует, но на выявление аномалий не влияет.
- **Перенос:** тип сохранён в enum `anomalyFlagTypeSchema`; правило будет пустым слотом
  (`suspiciousSupplierRule`) без выдачи флагов — чтобы не менять бизнес-результат.
- **Возможное улучшение (обсудить отдельно):** флагировать позиции от поставщика с `isApproved=false`.

## KI-2 — `detectVehicleFromText`: нормализация искажает «вольво» (кириллица) без номера
- **Статус:** OPEN
- **Где (исходник):** `фуры/serverDb.ts` → `detectVehicleFromText` (строки нормализации `t.replace(/^[вvbуgyhи]о*/gi, 'v')`)
- **Суть:** Нормализация превращает ведущее «во» в «v», из-за чего слово «вольво» становится «vльво»
  и перестаёт совпадать с `/volvo|вольво/`. Поэтому **bare «вольво» без номера → null**.
  Латинское «volvo» и любые варианты с номером («вольво 806», «V569») работают корректно,
  поэтому на реальных данных (где всегда есть номер/designation) проблема почти не проявляется.
- **Перенос:** как есть; зафиксировано тестом (`vehicleDetection.test.ts`, блок «задокументированный quirk»).
- **Возможное улучшение (обсудить отдельно):** проверять бренд до агрессивной нормализации.

## KI-3 — `detectPlacementFromText`: сокращения п/л, п/п, з/л, з/п не срабатывают (кириллица + `\b`)
- **Статус:** OPEN
- **Где (исходник):** `фуры/serverDb.ts` → `detectPlacementFromText` (правила осей прицепа `/1[-_ ]*п\/?л\b/` и т.п., а также steering/driving с `\bп\/?л`).
- **Суть:** В JS `\b` определяется по ASCII `\w` ([A-Za-z0-9_]); кириллические буквы — не `\w`,
  поэтому `\b` вокруг «л/п/…» не даёт границы, и шаблоны с `\b` для сокращений (п/л, п/п, з/л, з/п,
  «ось левая» и т.п.) **никогда не матчат** типичный кириллический ввод → возвращается null.
- **Следствие:** размещение по осям прицепа/рулевого фактически определяется только числовыми
  кодами «= 6..11 / = 2,3» и словосочетаниями без `\b` (напр. «передний левый», «ходовая левая крайняя»).
- **Перенос:** как есть; зафиксировано тестами (`placementDetection.test.ts`, блок KI-3 → null).
- **Возможное улучшение (обсудить отдельно):** заменить `\b` на явные границы (`(?<![а-яё])`/`(?![а-яё])`)
  или убрать `\b`. Изменит поведение — только после согласования.

## KI-4 — bulk-delete в оригинале НЕ проверял PIN для сверенных накладных (ИСПРАВЛЕНО осознанно)
- **Статус:** RESOLVED (осознанное отличие от legacy, согласовано)
- **Где (исходник):** `фуры/server.ts` → `POST /api/invoices/bulk-delete` (нет проверки isReconciled/PIN).
- **Суть:** Одиночный delete требует PIN 1308 для сверенной накладной, а массовое удаление —
  нет. Сверенные (заблокированные) накладные можно было удалить пачкой без PIN.
- **Решение в v2:** `InvoiceService.bulkDelete` теперь проверяет isReconciled + PIN 1308,
  как одиночный delete. Если в пакете есть сверенная накладная и PIN неверный —
  операция отклоняется целиком (PIN_REQUIRED), до каких-либо записей. Это **отличие от legacy**.

## KI-5 — PIN 1308 захардкожен в коде
- **Статус:** OPEN
- **Где:** одиночный/массовый delete и edit сверенной накладной.
- **Суть:** PIN для операций над сверёнными накладными зашит константой `'1308'`.
- **Перенос:** как есть (константа `RECONCILED_PIN`). Кандидат на вынос в конфигурацию/фазу безопасности.

## KI-6 — авто-создаваемому поставщику присваивается случайный 10-значный ИНН
- **Статус:** OPEN
- **Где (исходник):** `ensureSupplierExists` → генерация случайного ИНН при импорте/ручном вводе.
- **Суть:** Если поставщик не найден по имени, создаётся новый со случайным ИНН (уникальность
  проверяется только среди активных). Качество данных: ИНН нереальный.
- **Перенос:** как есть. Кандидат на явный ввод ИНН/пометку «ИНН не указан».

## KI-7 — edit пересоздаёт id позиций → сброс resolved у аномалий
- **Статус:** OPEN
- **Где (исходник):** `PUT /api/invoices/:id` — позиции с qty>1 (и новые) получают новые id.
- **Суть:** resolved-состояние аномалий хранится по ключу `invoiceId|invoiceItemId|flagType`.
  После правки id позиций меняются → ранее одобренные аномалии снова становятся активными.
- **Перенос:** как есть (поведение сохранено). Кандидат на стабильные id позиций.

## KI-8 — delete: soft-инвойс, но hard-delete позиций; нет rollback для ряда операций
- **Статус:** OPEN
- **Где (исходник):** delete/bulk-delete (позиции удаляются из коллекции), rollback-switch.
- **Суть:** Инвойс помечается deletedAt (soft), а его invoiceItems удаляются жёстко.
  Откат (audit rollback) в оригинале НЕ поддержан для `invoice_manual_create`, `invoice_delete`,
  `invoice_reconcile` → эти действия необратимы через UI (данные восстановимы только из audit-снимка).
- **Перенос:** как есть. Rollback будет реализован отдельной подфазой (по плану).
